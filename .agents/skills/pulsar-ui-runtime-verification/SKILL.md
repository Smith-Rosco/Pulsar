# Pulsar UI 缺陷：证据化定位与验证

> **Mirror**: 本 skill 有两份逐字一致的副本 —— 仓库内 `.agents/skills/pulsar-ui-runtime-verification/` 与 WorkBuddy 用户级 `~/.workbuddy/skills/pulsar-ui-runtime-verification/`；改任意一处须同步另一处（含 `references/`、`scripts/`、`assets/`）。

面向「UI 缺陷修完了，凭什么说修好了」这个问题。核心手段是**运行时证据 + 前后对照**，而不是目视 + 自信。

## 何时使用

- 用户报告 Pulsar 的 UI / 动画 / 布局缺陷（tab 指示器、面板溢出、主题注入、悬停对比度、翻页、子菜单…）。
- 需要证明某个 UI 修复真的生效（用户会问「修好了吗」，或你要自己下判断）。
- 无头 / 自动化环境量不到真实布局（`ActualWidth == 0`）时，仍要阻止布局回归复发。

不适用：纯逻辑缺陷（走常规单测即可）；与 UI 无关的重构。

## 铁律（先读，违反任一条即失败）

1. **不编造数字**。没跑过的测试不写「通过」；没量到的界面不写「已确认」。含糊处写「未验证」并附复现步骤。
2. **区分证据等级**，标签不许混：机读日志 / 自动断言通过 ≠ 用户目视验收 ≠ 像素级度量。报告里逐项标明属于哪一种。
3. **非侵入优先**：先定位、先出诊断，再动生产代码。临时诊断代码最终**必须整段拆除**。
4. **先枚举汇聚点**。修 UI 缺陷时先列出**所有**写入同一状态的入口，再判断哪条漏了防护。只改「出问题那一处」通常复发（Pulsar 真实案例：4 条重定位入口，3 条有动画门、1 条没有 → 动画被中途摘掉）。
5. **本 skill 的自动化会动用户桌面**：E2E 的 `click` 是真实鼠标输入（会短暂移动物理鼠标），resize 注入会改窗口尺寸。**运行前告知用户**。

## 工作流（8 步）

### 1. 定位代码路径 + 枚举汇聚点
读源码，画出「事件源 → 汇聚函数 → 状态写入」路径。把汇聚函数视为**唯一该加防护的地方**，并记下每个事件源的名字（第 3 步埋点要用）。

### 2. 先列互斥假设 + 每个假设的日志签名
写下 2–3 个候选机制，并为每个规定「日志里长什么样才成立」。例：

| 假设 | 机制 | 可判定的日志特征 |
|---|---|---|
| A 状态在动画前被清 | 条目被回收 → bounds 无效 → 退化为直接重定位 | `SKIP boundsInvalid` 紧跟 `SNAP` |
| B UI 线程被卡住 | 动画在时间轴上跑完但未渲染 | `PHASE1` 与 `PHASE2` 时间戳间隔 ≫ 时长 |
| C 并发写入改写起点 | 隐式动画起点被基础值覆盖 | `PHASE2` 起步位置 ≠ `PHASE1` 落点 |

**先有假设表，再加埋点**——否则日志会缺关键字段，白跑一轮用户操作。

### 3. 加临时追踪通道
写 `%TEMP%\<name>.log`，**不要写进仓库**。要求：
- 在每条分支的**入口**打点（含「没走这条分支」的原因），不只是成功路径。
- 字段要足以判定假设表（中心坐标、起始/目标值、调用方、连发序号、活动条目 Tag）。
- 毫秒时间戳 —— 用于判断事件是否落在动画窗口内。

### 4. 自驱动取证据，其次才请用户
优先用 E2E 自己复现（见 `references/pulsar-harness.md`）。仅当触发源依赖用户环境、自动化跑不出来时，才请用户操作——且**一次说清**：操作序列、预估耗时、日志能分辨什么。

### 5. 环境相关触发跑不出来 → 在同一汇聚路径上注入等价事件
若真机触发的那个事件（如 `Window.DpiChanged`）在自动化环境恒为 0，不要因此放弃验证：改用**汇聚到同一函数**的另一个事件源（如 `SetWindowPos` 抖动窗口尺寸 → `SizeChanged`）。
**有效性论证必须写明**：防护加在汇聚点，故「哪种触发源到达」不影响结论。同时声明这只是等价替代，不等于在用户机器上见过原始那一幕——这条写进报告的「未验证」小节。

### 6. 前后签名对照
用**同一驱动、同一事件量**跑修复前 / 修复后，输出可证伪的量化对照表，例如：

| 判据 | 修复前 | 修复后 |
|---|---|---|
| `clearAnim=True animating=True`（动画被摘的签名） | 3 | **0** |
| `PHASE2 atH=<终点值>`（零位移瞬态） | 2 | **0** |
| 守卫命中 / 注入总数 | — | 36 / 280 |
| 导航走完两段动画 | 部分被截断 | 8 / 8 |

关键：**先证明判据本身有效**——用变异检查（把缺陷改回去，确认会红并精确报出位置）再撤销复绿。验证的不是「测试通过」，而是「缺陷真能被拦住」。

### 7. 拆除诊断 + 重建 + 冒烟
拆埋点会留残留：为日志加的 `CallerMemberName` 形参、多余空行、被展开的单行守卫。二次清理后 `build 0 警告 / 0 错误`，再对**最终产物**（诊断已拆）跑一次 E2E 确认功能完好。

### 8. 沉淀 + 明说没验的部分
按仓库文档纪律落地：`Docs/lessons/`（可复用坑位）、`Docs/journal/YYYY-MM-DD.md`（会话正文）、`Docs/journal/NEXT.md`（待办）、必要时 `Docs/reports/*.html`（结构化报告）。报告与 journal 必须含「未验证项」小节。AI 只做本地 commit，push 留给用户。

## 静态守卫：无头环境的布局回归替代方案

无头主机上 `ActualWidth == 0`，布局回归**不可度量**。不要因此跳过守卫——改用**静态 XAML 扫描**：

- 从被承载方的 code-behind（如页面里的 `new Dialogs.Contents.X()`）**自维护地解析**待检集合 → 以后新增复用点不会漏，也不必改测试。
- 只扫**根标签**（内层合法用法很多，例如固定标签列宽度）。
- 先**剥注释**再匹配（注释里往往就写了被禁的属性名）。
- 匹配集合为空 → **fail-fast**（防改名后测试静默空转）。
- 用变异检查验证守卫有效。

## 输出纪律

- 结论先行：根因一句话 + 证据一行 + 改动文件清单（含 `+N/−N`）。
- 数字必须可复现（哪个日志、哪条判据、多少次）。
- 「未验证」要写清**为什么**未验（无头不可测 / 环境触发不可复现 / 仅目视）以及**怎么才能验**。
- 若属修正自己先前的结论，**显式写「更正」**，不要静默改口。
