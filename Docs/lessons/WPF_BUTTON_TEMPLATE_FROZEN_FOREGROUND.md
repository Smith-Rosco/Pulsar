# WPF Button Template Frozen Foreground

**Status**: Published  
**Scope**: Lesson  
**Applies To**: Wpf.Ui Button custom templates (`Styles/ButtonStyles.xaml`)  
**Last Updated**: 2026-08-18

---

## Rule (TL;DR)

**Never set `Foreground` / `TextElement.Foreground` on a named `ContentPresenter` via a template trigger to style button text.** Either:

- Use an explicit `<TextBlock>` as the text presenter so trigger setters apply directly, **or**
- Set `Foreground` on the **control itself** (inherited property) when the text color must react to control state (checked / hover).

---

## Symptom

Buttons render with the accent (dark-navy) background but **black text**, even though the style's `Foreground` is white. Hover/pressed/checked state changes do **not** change the text color.

Reported as: Add Slot / Save Slot / unsaved-changes dialog Save buttons showing "深蓝底黑字" (dark blue background, black text). Because the style is shared, **every** Pulsar-styled button on settings pages and dialogs was affected.

---

## Root Cause

WPF's `ContentPresenter`, when it converts a string to a `TextBlock`, **freezes the foreground as a local `BaseValueSource.ParentTemplate` value at first layout**. Template triggers that later set `TextElement.Foreground` on the ContentPresenter never reach the already-generated `TextBlock`.

Verified with a rendering diagnostic on a themed window:

```
Content='OK'  ButtonFg=#FFFFFFFF  ButtonBg=#FF0067C0  Text=#FF000000  src=ParentTemplate
```

The button's own `Foreground` (a style setter, `DynamicResource`) resolved correctly to white, and the ContentPresenter's `TextElement.Foreground` was white, but the generated `TextBlock` kept the initial inherited black value — the trigger's value was captured at generation time and never refreshed.

---

## Correct Pattern

Use an explicit `TextBlock` for the text presenter; the triggers then set its `Foreground` (the same DP as `TextElement.Foreground`) directly:

```xml
<ControlTemplate TargetType="ui:Button">
    <Border x:Name="RootBorder" Background="{TemplateBinding Background}" ...>
        <StackPanel>
            <TextBlock x:Name="TextPresenter" Text="{TemplateBinding Content}"/>
        </StackPanel>
    </Border>
    <ControlTemplate.Triggers>
        <Trigger Property="IsMouseOver" Value="False">
            <Setter TargetName="RootBorder" Property="Background" Value="{DynamicResource Theme.Accent}"/>
            <Setter TargetName="TextPresenter" Property="TextElement.Foreground" Value="{DynamicResource Theme.Accent.Foreground}"/>
        </Trigger>
    </ControlTemplate.Triggers>
</ControlTemplate>
```

---

## Incorrect Pattern

```xml
<!-- ❌ WRONG: generated TextBlock freezes the foreground at first layout -->
<ControlTemplate TargetType="ui:Button">
    <Border ...>
        <ContentPresenter x:Name="TextPresenter" Content="{TemplateBinding Content}"/>
    </Border>
    <ControlTemplate.Triggers>
        <Trigger Property="IsMouseOver" Value="False">
            <Setter TargetName="TextPresenter" Property="TextElement.Foreground" Value="{DynamicResource Theme.Accent.Foreground}"/>
        </Trigger>
    </ControlTemplate.Triggers>
</ControlTemplate>
```

---

## Why This Works

- An explicitly declared `TextBlock` in the template is not generated by `ContentPresenter`, so no `ParentTemplate` freeze occurs; trigger setters apply to its `Foreground` DP live.
- **Safe alternative:** setting `Foreground` on the **control** (e.g. a `RadioButton` with `IsChecked` → `Foreground="White"`) works because `Control.Foreground` is an *inherited* property — the generated `TextBlock` inherits the updated value dynamically. The segmented action buttons use this pattern and were verified to update correctly even when toggled after first layout.

---

## Audit (2026-08-18)

Searched the codebase for `Setter TargetName=...Foreground` in templates and all `ContentPresenter` text-presenter usages:

| Location | Pattern | Verdict |
|----------|---------|---------|
| `Styles/ButtonStyles.xaml` (Primary/Secondary/Danger/Icon) | trigger on named ContentPresenter | **fixed** → explicit `TextBlock` |
| Segmented action `RadioButton` styles (AddSlot / SlotConfiguration dialogs) | `Foreground` on the control | safe (inherited) |
| Card buttons, ListBoxItem, Expander, ToolTip, tutorial overlay, ExpandableCard, plugin multi-select toggle | no presenter foreground triggers / control-level | safe |

The bug existed **only** in `ButtonStyles.xaml`.
