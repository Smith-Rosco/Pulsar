0. 核心结论（TL;DR）

  1. 方向正确：Pulsar 以根目录 AGENTS.md 为唯一常驻规则文件，是 2026 年跨工具事实标准下的正确选择——OpenCode（你的主力 harness）原生读取；GitHub Copilot 无专属文件时也回退读它。
  2. 体量超标：当前 AGENTS.md 共 201 行 / 约 20.4 KB，已触及业界公认上限（CLAUDE.md 建议 ≤200 行、AGENTS.md 建议 30–150 行）。最大的"体积元凶"是内联了 19 行 Critical Pitfalls 表，与 Docs/lessons/（20 篇）完全重复——这正是被研究证实的"重复已有文档"反模式。
  3. 存在可验证性债务：journal 已记录"AGENTS.md 承诺的 session-journal 是空头支票"教训——规则里写承诺必须真实接线，且其中引用的命令 / 路径 / skill 需要可验证（如根目录 dotnet build Pulsar.sln 会 MSB1009 这类路径坑）。
  4. 多 harness 可达性仍需制度化：session-journal skill 曾因只放 .opencode/skills/ 而不可见于豆包环境，靠人工镜像到 .agents/skills/ 才修复；这应固化为规则而非靠运气。
  5. 不需要新增 rules 文件：无需 CLAUDE.md / .cursor / copilot-instructions（避免重复维护）。若未来引入 Claude Code，用 @AGENTS.md import 或 mklink 桥接即可。

1. 调研：rules 文件生态

1.1 什么是 rules 文件

rules 文件（AGENTS.md / CLAUDE.md / .cursorrules 等）是放在仓库根目录（及子目录）的 Markdown，给 AI 编程 agent 提供每次会话都加载的常驻项目上下文：技术栈、构建/测试命令、代码约定、边界（Do NOT）。它区别于 README（给人看）：是"写给机器的 README"。每个 agentic 工具曾各发明自己的文件（Claude Code→CLAUDE.md、Cursor→.cursorrules/.cursor/rules、Windsurf→.windsurf/rules、Gemini CLI→GEMINI.md、Aider→CONVENTIONS.md），造成"同一套规则写五份"的碎片化。

1.2 统一标准：AGENTS.md 的崛起

  • 2025-08：OpenAI 发布 AGENTS.md 作为开放约定，获 Google、Cursor、Factory 等背书。
  • 2025-12：捐赠给 Linux 基金会下的 Agentic AI Foundation（AAIF）（OpenAI、Anthropic、Block、AWS、Google、Microsoft、Bloomberg、Cloudflare 等联合创立），成为真正的跨厂商标准；已获 60,000+ 开源项目采用。
  • 2026 中：Codex CLI、Cursor、GitHub Copilot、Cline、Zed、Amp、OpenCode 原生读取；Gemini CLI / Aider / Claude Code / Windsurf 经一行配置或 import 桥接。

规格刻意"轻"：无强制 schema、无前置元数据要求，纯 Markdown 自然语言。OpenCode 的行为是：在当前目录及父目录读取 AGENTS.md（Pulsar 的根 AGENTS.md 因此对 OpenCode 一直生效）。

2. 调研：怎么写才有效（研究证据）

2.1 关键研究：自动生成的规则文件反而有害

ETH Zurich SRI 实验室（论文 Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?，arXiv:2602.11988）在 SWE-bench Lite + 自建 AgentBench 上测了 Claude Code / Codex / Qwen Code：

  • LLM 自动生成的 context file：平均降低约 3% 成功率，推理成本 +20%；
  • 开发者手写的：仅有微弱正向（约 +4%），同样增加成本；
  • 根因：上下文窗口是稀缺资源，文件每一行都在与代码、错误信息、对话历史争配额；且模型大约只能可靠遵守 150–200 条独立指令，超出会"选择性遗忘"。

作者澄清：反派不是 AGENTS.md 本身，而是 /init 自动生成 + "塞越多越好"的心态。简洁、人手写、只含"agent 无法从代码推断的信息"的规则文件是有效的。

2.2 GitHub 从 2500+ agents.md 归纳的 5 原则

  1. 可执行指令放前面——agent 反复查的命令放开头。
  2. 代码示例 > 长篇解释。
  3. 明确的三层边界——永远要做 / 先问 / 绝对不要做（最常见："绝不 commit secrets"）。
  4. 具体到版本的技术栈——"React 18 + TypeScript + Vite + Tailwind"，不是"React 项目"。
  5. 覆盖 6 个核心域——指令、测试、项目结构、代码风格、git 工作流、边界。

2.3 该写什么 / 不该写什么

该写（agent 无法从代码推断的）
  • 非预期的工具链选择（uv 而非 pip、bun 而非 npm）
  • 历史包袱、团队共识、外部约束、踩过的坑
  • 构建/测试/验证命令（尤其非显而易见的）
  • 边界与禁令（Do NOT）
  • 架构意图（WHY，而非目录结构）
不该写（写入即白费上下文配额）
  • 重述 README / 已有文档
  • 目录列表、架构分层概述（agent 一个 ls 就知道）
  • 明显可见的技术栈细节（package.json 已写）
  • linter / formatter 能做好的代码风格（4 空格、命名）
  • 空泛标语（"写 clean code"）
  • 只在特定场景才用到的指令（应做条件加载或放子目录）

2.4 Rules vs Skills：分工

Rules（AGENTS.md / CLAUDE.md）Skills（SKILL.md）
定位常驻项目上下文：不变量、约定、约束、边界按需流程：多步工作流、检查表、脚手架
加载时机每会话、每 prompt 都注入（被动）description 命中时按需加载（主动触发）
适用安全/范围/格式不变量、非协商原则、上下文无关约束可复用任务流程（代码评审、测试生成、发布、回填 journal）
反例多步骤任务细节（应抽成 skill）每次都必须遵守的安全红线（应放 rules）

2.5 维护机制（把规则当代码）

  • 纠正即回写：每次在会话中纠正 agent（"我们用 X 不用 Y"），该纠正应落进规则文件——这是最高杠杆习惯。
  • 进 PR 评审：规则变更走代码评审，git blame 可追溯。
  • 季度修剪：删除已不存在的模式；越短越被遵守。
  • 查矛盾：多人添加规则会产生互相冲突的条目，agent 处理矛盾很差，需择一。
  • 指定 owner：纳入 CODEOWNERS。

4. 建议

4.1 目标架构（分层原则）

保持"常驻规则做减法、归档与技能做加法"的分层，把 AGENTS.md 收敛为纯 always-on 内核：

  1. 常驻规则（唯一 always-on）：AGENTS.md → 瘦身至 ~160 行（当前 248 行）。只保留：项目快照（1 段）、不变量（MUST/SHOULD）、Top-5 地雷 + 一行指向 Docs/lessons/、Task Router、Quick Commands（经 dev.ps1）、Agent Behavior Rules（AI 三角形 + 会话仪式 + worktree 纪律）。
  2. 归档知识（按需全文）：Docs/decisions/（ADR）、Docs/lessons/（坑位全文）、Docs/architecture/——AGENTS.md 只留指针，不复制正文。
  3. 按需技能：.opencode/skills/ + .agents/skills/ 保持双镜像；把 AGENTS.md 里的"工作流/任务型"段落（如发布、openspec 命令）改为指向现有 skill。
  4. 工作记忆：Docs/journal/ 维持 ADR-019 单源。
  5. 工具契约：Docs/agents/*.md、CONTEXT.md 维持；harness×加载机制矩阵（可选）放 Docs/agents/，不进 AGENTS.md。
