日期：2026-09-09 · 评估范围：RadialMenuWindow + MenuSession 交互层 · 非侵入式评审（未改动任何源码）
方法：代码证据链（file:line）+ 径向菜单交互文献对照 + 既有决策（ADR-008/011/020/023/024、UX_REFACTOR_PROPOSAL）对齐

〇、关键判断摘要（TL;DR）

  1. 轮盘交互模型本身不需要推翻重做。空间定位 + 肌肉记忆的核心模型与径向菜单研究文献（pie menu / marking menu）的最佳实践高度一致，且 ADR-024 刚完成级联子菜单几何收口（Fan/Ring、统一极坐标命中）。重构对象应是结构债务与感知延迟，不是交互范式。
  2. P0-1 · 感知延迟预算超支：召唤 ≈250ms + hover 进入 300ms + 磁吸速度上限 120px/s + 翻页边界回弹缓动——对「每天唤起 200 次」的 Persona 是持续摩擦，与「高性能启动器」定位直接矛盾。
  3. P0-2 · MenuSession.cs 已膨胀到 3609 行：手势状态机、子菜单进出视觉、翻页、watchdog、中心预览全在一个文件里。它是后续任何 UX 迭代的摩擦源，建议与 UX 改造并行推进拆分（且已有三次成功先例可循）。
  4. P0-3 · 键盘无法选择槽位：仅 Esc + 左右翻页，无方向键/数字键直达。无障碍与「手不在鼠标上」场景缺位，UIA Peer 也只是 Custom 控件最小实现。
  5. 推荐路线：两轨并行——UX 轨做 6 项快赢（不碰架构），重构轨按 4 步拆 MenuSession。每步都有现成 E2E/单测管线兜底。

一、范围与基线

本次调研只覆盖轮盘面板本身（召唤 → 悬停 → 选择 → 子菜单 → 消退的全交互闭环），即 RadialMenuWindow、MenuSession、SlotOrb、SlotLayoutEngine 及其协调器。设置窗口、教程系统等界面不在范围内。

基线一：2026-09-01 全局 UX 改造已完成的部分（本报告不重复提案）
  • 令牌管道（排版 6 级 / 时长 3 级 / 间距 8 档 / 圆角 6 档），577 处裸值收敛，僵尸令牌清零。
  • 浅色主题激活反馈三通道（描边加粗 + 填充提亮 + 外圈同心环）——已落地 SlotOrb.xaml:107-170。
  • 常驻金色脉冲 → 进入一次性淡入；逐球 DropShadow 移除；BackEase → 指数缓动（SlotOrb 层）。
基线二：既有交互决策（必须继承，不可逆改）
  • ADR-008：MenuSession 状态机 + VM 薄投影；ADR-020：右拖手势编排收口 MenuSession。
  • ADR-024（v1.2.2）：Fan 同心外弧 + Ring 替换式几何、D10 统一极坐标扇区命中、D11 级联期间动态标题抑制、D5 flick-out 动态半径。
  • 全屏视口吞事件 + 500×500 内容坐标系 + 边缘 clamp + 光标 warping（archive FULLSCREEN_VIEWPORT）。

三、问题清单（P0–P3）

P0 感知延迟预算超支：每个环节都比必要值慢一拍

证据链

  • hover 激活 enter=300ms（SlotOrb.xaml.cs:218-263）——径向菜单的优势是「指向即选择」，300ms 的激活过渡意味着快速划过 3 个槽位时反馈永远追不上光标。
  • 磁吸速度上限 120px/s + 0.10s 时间常数（SlotViewModel.cs:234-299）——对快速甩向目标的 Power User 是主动减速带；磁吸本意是「稳定目标」，不是「拖住用户」。
  • 召唤两段动画叠加 ≈250ms 后才达终态（RadialMenuWindow.xaml.cs:177-190）——文献基准：启动器类 UI 召唤反馈应在 100ms 内可交互（Nielsen 响应性 0.1s 准则）。
  • 翻页边界 nudge 用 BackEase 0.35（RadialMenuWindow.xaml.cs:273-330）——2026-09-01 已裁定「回弹缓动推迟终态感知，全局改指数」，这是漏网的最后残留，动效语言不一致。

建议：hover enter 压到 ≤120ms（release 保持现状即可）；磁吸速度上限提至 ≥400px/s 或改为「接近才吸附」（距目标 <20px 时启用）；nudge 换 Pulsar.Easing.Standard。三项都是常量级修改，低风险高感知。

P0 MenuSession.cs 3609 行：所有 UX 迭代的共同摩擦源

证据链：MenuSession.cs 约 100 个方法（MenuSession.cs:526-3575），手势状态机（1154-1449）、子菜单进出视觉（2802-3276）、翻页与 watchdog（1956-2061, 3412-3455）、中心预览、flick-out 全部同居。几何常量 (250,250) 在 3 处硬编码（SlotLayoutEngine.cs:23-24 · MenuSession.cs:46-47 · RadialMenuLayoutCoordinator.cs:13，ADR-024 自己也点名了）。
佐证（债务已经咬人）：Fan 子菜单重叠主轮、Ring 命中模型不一致、动态标题遮挡——最近三个生产 bug 全部源自这层几何/状态纠缠（ADR-024 Context 节）。

建议：沿用已被验证的 coordinator 抽取模式（Layout / SubMenu / VisualState 三次成功先例），按 4 步拆：
① GestureController（右拖状态机 + flick-out，1154-1449）
② SubMenuTransitionController（进出 bloom 动画编排，2802-3276）
③ WheelGeometry 静态常量类（250 基准 / 半径 / 死区单一真相源）
④ MenuWatchdog 独立服务（3412-3455，最无争议的一块）
每步独立 commit + 测试先行的钉死用例（沿用 C1-C5 批次的 grill auto-with-guardrails 流程）。

P0 键盘与无障碍：轮盘是纯鼠标设备

证据链：PreviewKeyDown 只处理 Esc 与 ←→（RadialMenuWindow.xaml.cs:243-271）；SlotViewModel 无任何键盘导航成员；UIA Peer ControlType=Custom（SlotOrbAutomationPeer.cs:29-61），屏幕阅读器只能读到一串无名 Custom 节点。

为什么是 P0 而非 P2：① 触控板 / 手部受伤 / 单手操作场景完全无法使用；② Windows 径向同类（如游戏轮盘）普遍支持方向键扇区选择；③ 现有极坐标扇区模型天然映射方向键（8 槽 = 8 方向），实现成本极低——命中已有 HitTest(Vector)，方向键合成一个远点向量即可复用全链路（含 hover/preview）。

建议：方向键（含对角组合）映射最近扇区 + Enter 执行 + 数字键 1-8 直达；UIA Peer 补 ControlType.Button / ExpandCollapse 语义。需用户裁决是否纳入。

P1 槽位标签 40px 截断：可读性瓶颈

证据链：标签 backplate FontSize=11、MaxWidth=40、TextTrimming 省略号（SlotOrb.xaml:302-351）。50px 的 orb 上 40px 宽的标签意味着 4-5 个汉字后必然截断——「资源管理器」这类常见名称都显示不全。用户被逼迫靠纯图标 + 位置识别，新用户（Persona 李）学习成本高，且更长的本地化串（如德语）会全军覆没。

建议：标签宽度与扇区角宽挂钩（8 槽 45° 扇区在 R=90 处弦长约 69px，还有余量）；或激活态展开完整标签（hover 时 backplate 延展）。同时校验 12 槽 / 6 槽两端的极限值。

P1 S1 测试债：几何回归的防波堤缺失

证据链：RadialMenuLayoutCoordinator / CommandPageProvider / ProcessPageProvider 直接测试为 0（NEXT.md S1；ADR-023:53 承诺的 page-provider tests 未兑现）。对比：Fan 重叠 bug 与 Ring 命中 bug 都是「改一处几何、崩三处行为」的典型——而这三类恰恰是最适合纯函数化单测的（输入槽数 → 输出 pose）。

建议：与 P0-2 的拆分绑定做——拆出 WheelGeometry 时同步补 pose 快照测试（8/10/12 槽全参数钉死），把 ADR-023 的欠账一并清掉。

P1 中心节点语义密度过高

证据链：中心同时承担 5 种角色——Cancel 锚点（根态）/ Back 锚点（子菜单）/ 窗口实时预览宿主 / morph 动画目标 / 死区原点。VisualStateCoordinator 里 D8「preserveCenterIdentity」等条件分支（RadialMenuVisualStateCoordinator.cs:49-101）+ MenuSession 里 3 个独立方法（UpdateSubMenuCenterLabel / ResetCenterSlotForRootMenu / ApplyCenterPreview）共同维护它。每次级联交互改动都要人工核对中心身份不被误重置——D7/D8/D11 的两次返工都与此相关。

建议：不改视觉行为，改归属——中心身份策略收敛为单一 CenterIdentityPolicy（输入：MenuState + activeSlotIndex + cascade 类型 → 输出：label/icon/preview 指令），coordinator 只执行。这与 P0-2 的②同步做。

P2 视口边缘的体验断层

证据链：clamp 位移中心后靠 SetCursorPos 强制 warp 光标（RadialMenuWindow.xaml.cs:155-160, MenuViewportService.cs:165-169）。光标瞬移是可感知的「跳变」，且与 Windows 原生指针加速曲线冲突；在多显示器边界 / 高 DPI 屏上换算误差会被放大。

建议：评估「菜单贴边变形」替代方案（扇区向屏内压缩半角——pie menu 文献中的 screen-edge adaptation），至少为 warp 前后补一帧视觉连续性说明。属探索项，先做真机复现收集样本再定。

P2 空轮盘 / 弱内容态没有专门设计

证据链：设置界面已有统一 EmptyState 组件（6 处），但轮盘本身的空态路径未见同等待遇——Command 页无槽位、Window 页无窗口、插件全部被断路器熔断时，轮盘呈现什么状态没有专门设计与测试钉死。（此条未做穷尽验证，实施前先跑一遍空配置真机确认。）

P3 卫生项

  • XAML 死注释：RadialMenuWindow.xaml:296-302 存在自我争论式的过时注释（讨论 ZIndex 该怎么放却未删）；:26-29 的历史说明建议迁去 lesson 文档。
  • watchdog 60s 常量与 1s 轮询写死在 MenuSession（:61, 3412-3455），拆分时顺手参数化。
  • dismiss 淡出 160ms 与 flick-out 变暗 200ms 两套节奏（xaml:111-136 vs xaml.cs:214-230）——统一到时长令牌。

四、文献对照：轮盘做得对的地方（要保护，勿误伤）

设计点文献依据现状评价
角度扇区命中（无径向上限，死区外即触发） Pie Menu（Callahan et al. 1988）：角度方向的目标宽度远大于线性菜单，选择更快更稳 ✅ D10 后根轮与 Ring 统一同构，是正确的核心资产
固定槽位位置 + 空间记忆 Marking Menu（Kurtenbach & Buxton 1994）：固定方位映射是肌肉记忆的前提 ✅ 槽位按索引固定布局，勿引入任何「自动重排」
中心死区 径向菜单研究共识：内圈死区消除中心选择歧义、防误触 ✅ 死区半径 0.60R-0.65R 与惯例吻合（0.5R-0.7R 区间内）
每页槽数 6-12 经验阈值：超过 12 项角度分辨率先于视觉尺寸崩坏 ✅ 上限 12、编辑器已有 Fan>3 告警（ADR-024 D2）
手势按住-划-松开的选择语法 Marking Menu 的 stroke-through 选择：专家无需视觉确认 ✅ 右拖 + 松键执行已是专家通道，与 flick-out 取消互补
子菜单连续 morph（非替换跳变） 空间连续性：上下文保持减少认知重置 ✅ 中心 morph + Fan/Ring bloom 是对外叙事的差异化卖点（README 三支柱之一），重构时严禁退化为「内容替换」

另一个要保护的非交互资产：E2E 管线（UIA AutomationId + 命令通道 + 截屏断言）已在子菜单三 bug 回归中证明价值——下列每项改动都必须有对应 E2E 或单测钉住。
