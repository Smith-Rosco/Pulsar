tab 指示器「切到第一个 tab 无动画」· 根因与验证

2026-09-10 · Pulsar（.NET 8 / WPF）· Views/SettingsWindow.xaml.cs · 自绘 NavIndicator 两段式切换动画

结论：这不是页面加载慢，也不是"第一个 tab"特有问题——是事件驱动的延迟重定位缺少动画门，把正在跑的 stretch 动画整段摘掉，指示器 1 帧瞬移到目标。
"第一个 tab" 是伪线索：真正的变量是「哪一次导航恰好带出布局事件」。用户环境在导航到 Slots 时连发 7 次 Window.DpiChanged（23ms 内），必然踩中 250ms 的动画窗口。
修复：给唯一的公共重定位入口补 _isNavAnimating 门 + 动画起点改显式 From（顺带修掉"先跳后滑"的次生缺陷）。修复前后对照：动画被摘掉的签名 3 → 0，零位移瞬态 2 → 0。

二、根因

指示器由 ShellViewModel_PropertyChanged 驱动两段动画（stretch 120ms + snap 130ms）。SettingsWindow 有 4 条重定位入口，其中只有 OnNavPaneLayoutUpdated 有 if (_isNavAnimating) return;。RepositionNavIndicator()——DPI 变化 / 窗格开合 / 面板尺寸 / 导航项重建的公共入口——的延迟回调没有门，直接跑 InitializeNavIndicator() → RepositionNavIndicatorImmediate(clearHeldAnimations: true) → BeginAnimation(prop, null)。

clearHeldAnimations 本来是为「写基础值前摘掉上一轮 HoldEnd 残留」设计的；在动画进行中执行就变成破坏性操作。

次生缺陷：隐式 origin 会被并发写入改写

phase 1/2 原先用 DoubleAnimation(to, duration)（From=null），起点取自属性的当前生效值。当并发的重定位抢先写入基础值，phase 2 的起点就被改写：用户日志里出现过 atTop=69.7 atH=102.0 → top=149.7（先跳后滑）。现已改为显式 From：phase 1 取当前生效值、phase 2 取 phase 1 的落点，帧间连续，与并发写入彻底解耦，并顺带消除 Height 为 NaN 时的取值崩溃通道。

三、修复（Views/SettingsWindow.xaml.cs，+40 / −10）

  • P0RepositionNavIndicator() 延迟回调加 if (_isNavAnimating) return;——在执行时判定（事件可能在动画开始前排入队列）。收尾由动画 finally + OnNavPaneLayoutUpdated 自愈接管，位置不会丢。
  • P0两条 in-animation 退化路径（boundsInvalid / NaN centers）显式 _isNavAnimating = false 后再 defer——它们已放弃动画独占，否则会被自己刚加的门拦下，指示器卡在旧位置。
  • P1phase 1/2 改显式 From（startTop/startHeight → stretchTop/stretchHeight）。

四、验证方式（无头可用，自驱动）

本题属于「事件时序 × 动画」竞态，截图/目视都不可靠，所以采用同一驱动 + 事件注入的前后对照：

  • 用仓库既有 Pulsar.E2E 驱动设置窗口：click 步骤走 FlaUI 真实鼠标输入（Mouse.MoveTo + Click）→ 与手点同一条 PreviewMouseLeftButtonUp 路径；工作流 22 步、8 次导航，含 4 次「非首个 → Slots」。
  • 用户环境独有的 DpiChanged 连发用 fixture 复现不出来 → 改为注入同一汇聚路径：SetWindowPos(+SWP_NOZORDER|SWP_NOACTIVATE) 在导航期间持续抖动窗口尺寸，触发 NavPaneGrid.SizeChanged → RepositionNavIndicator()。280 次注入全部命中（与追踪中 280 条 pane-size-changed 逐条对应）。守卫位于汇聚点，因此与触发源种类无关。
  • build 0 警告 / 0 错误；全量测试 1492 / 1492 通过；拆除临时诊断后对最终产物再跑一次 E2E PASS。
诚实边界
  • 注入的是 SizeChanged，而用户环境实际触发的是 DpiChanged —— 两者在 RepositionNavIndicator() 汇聚，是同一行守卫；本次未在真机复现 DpiChanged 那条具体入口。
  • 本报告未做像素级目视确认（动画观感），全部结论基于可机读的事件日志判据。

五、开放观察（未处理）

Window.DpiChanged 在导航到 Slots 时连发 7 次（23ms 内），而自动化跑同一导航为 0 次。已排除「页面尺寸撑大窗口」：窗口固定 1000×700、无 SizeToContent、WindowStartupLocation=CenterScreen、PaneDisplayMode=Left。修复后该连发已无害（动画期间被丢弃），但来源未解，疑与多显示器 / DPI 环境有关。

建议：下次真机排查时在 OnWindowDpiChanged 记录 e.OldDpi / e.NewDpi（本次已临时加过，随诊断一并拆除）。
