3关键洞察（本次再次对比的新结论）

① 「两条路线」已完全分化，且不可互相照抄。StarPie 证明了：单体 + 极致轻量 + 高频小版本 + 用户反馈闭环，能把「手势轮盘」这个产品形态打磨到 10 分。Pulsar 不该在它的主场上比拼迭代速度——但在「用户触点迭代速度」这一个维度上值得局部学习：M1 的每一项（安装器/更新/截图/视频）都是 StarPie 已验证过的标准动作，有现成答案可抄。
② Pulsar 的「借鉴红利」已基本吃完，剩余缺口都是战略选择而非技术未知。roadmap 三大方向（手势细节/渲染器/级联子菜单）主干全部落地，IMPLEMENTATION_VERIFICATION.md 的 10 项未落地清单里，除「渲染器插件化」外全部是打磨型或已显式决定不采纳的项。继续对标 StarPie 的边际收益快速递减——下一步的对手名单应该换成 Quicker（动作生态）和 Raycast（AI）。
③ Neon 渲染器插件修复 = 「渲染器插件化」差异化的临门一脚。09-03 评估里 Pulsar 相对 StarPie 的唯一差异化点是「渲染器走插件机制、第三方可发布主题插件」。当时它是 ❌；现在外部插件（Neon）的生命周期坑已修完、E2E 已验证——把 StyleRendererFactory 的 IEnumerable<IRadialRenderer> 接上 IPluginRegistry，Neon 就是第一个活的证明。
④ 分发差距是唯一在扩大的差距，且 StarPie 的解决方案源码可抄。其检查更新三级容灾（REST API → Atom Feed 免鉴权免限流 → 302 探测）+ 多镜像故障转移 + 单文件自包含发布，全部有源码参考（WinPieGestures 更新模块），移植到 Pulsar 属于「工程翻译」而非「产品设计」。
⑤ 工程护栏已到「够用」水位，继续加码属于边际收益递减。1059 测试 / 0 警告 / E2E PASS / AGENTS.md v4 之后，工程侧剩余待办（NEXT.md 3 项）全是观察类。资源应整体转向 M0/M1/M2。
