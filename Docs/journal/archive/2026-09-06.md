## Session (10:28 · grilling 对齐 cascade submenu 几何重构 → ADR-024)

**做了什么**
- 用 grilling skill（interactive 模式）与用户对齐 Fan/Ring 子轮盘重构，Q1–Q9 全部定稿。
- 产出 `Docs/decisions/024-cascade-submenu-geometry-and-viewport.md`（Proposed，未实现）。
- 回源核实子代理结论，推翻/修正 3 处：
  - 子代理称「Fan 已 hideFillers=false 保留主轮盘」→ 实测 Fan 下 fillers 会 bloom 回来（`MenuSession.cs:2686`），主轮盘观感是"缩一下又弹回"，这才是用户抱怨的收缩动画来源之一。
  - 子代理未提 `AnimateMenuCenterAsync`（:2490，:2605 调用）——视口 glide 才是"主轮盘位移"的主因。
  - 子代理称 canvas 500×500 是渲染边界 → 实测全仓库无 `ClipToBounds`，画布不裁剪；500×500 纯粹是坐标约定。

**关键决策 / 坑**
- **发现的硬约束（本次最大收获）**：甩出取消判定锚在 `_menuCenter`，阈值 `R × 1.5 = 135`（`MenuSession.cs:1972-1991`）；escaped 时 `HandleGestureRightReleaseAsync` 在 `:1615` 直接 return，**取消整个手势、不执行任何槽位**。所以任何"子轮盘离开 _menuCenter"的设计，不配套改判定就会把外圈子槽位变成"点了没反应"的死区。
- 纯放大取消半径（用户原设想 a）不可行：Ring 需 ~196，会把根菜单阈值从 135 抬高 45%。必须**原点 + 半径同时动态**（用户设想 b 的加强版）。
- 视口概念澄清：窗口被 `MenuViewportService` 撑满整个工作区（为吞事件 + 角度扇区命中），500×500 MenuCanvas 是内容坐标系；`MenuVisualExtentDip = 260` 喂 `ClampMenuCenter` 防贴边被截。**画布铺满屏幕无收益**（动画只改 transform，画布大小不影响性能），且会让 extent 撑满 → 中心锁死屏幕中央 → 每次召唤 warp 鼠标。
- 空间账：gap=70 时 Fan 外缘 185 < maxSafeRadius 225 < extent 260，**余量充足，无需动画布尺寸**；只有 R 涨到 180（多槽位）时才需降级压缩 gap。

**下一步**
- 待用户复核 audit log 无否决 → 按 ADR-024 实现（D1–D9）。
- 实现后：CHANGELOG + 更新 ADR-024 状态为 Accepted + 测试基线核对（当前 1066/1066）。
